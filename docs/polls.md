# Audience Polls

**Source of truth for both polls.** `run-of-show.md` and `slide-plan.md` point here — change the wording in this file only.

Productside webinars run two polls: one after the problem setup to activate the audience, one at the close asking what the audience will do differently. Both use the `w-poll` layout (one question, options `01`–`05`).

**They share a single taxonomy: the five collaborative pains.** Poll 1 names five pains before the journey begins. Poll 2 asks the same five back as commitments. The delta between them is the signal.

| | Poll 1 | Poll 2 |
|---|---|---|
| Slide | 5, after the five pains | 34, after What Change Looks Like |
| Runs at | 0:08–0:10 | 0:52–0:54 |
| Open for | ~60 seconds | ~60 seconds |
| Read by | Kenny | Kenny |

---

## Poll 1 · Setup

**Question:**

> When Collaborating, What Hurts the Most?

**Options:**

| | Option |
|---|---|
| `01` | Copying the same context everywhere |
| `02` | Relitigating decisions we already made |
| `03` | Redoing discovery we already did |
| `04` | Relying on people to remember the rules |
| `05` | Losing ideas that never got explored |

**How to run it.** Launch it right after the five collaborative pains slide. Leave it open about a minute, then read the results out loud and **name the section that covers the winner**. That one sentence turns the agenda from a feature list into a list of answers.

**The live steer:** if one option runs away with it, spend an extra minute on that section and take the minute from one that landed low. Decide it in the moment.

---

## Poll 2 · Commitment

**Question:**

> Starting Today, What Will You Do Differently?

Productside's house closing question. Do not reword it.

**Options — each one is Poll 1's pain, resolved, in the same order:**

| | Option | Resolves |
|---|---|---|
| `01` | Stop copying the same context everywhere | `01` |
| `02` | Keep track of why decisions were made | `02` |
| `03` | Make the next discovery build on the last | `03` |
| `04` | Bake the standards into the work | `04` |
| `05` | Give every idea a place to be explored | `05` |

**How to run it.** Launch it after the What Change Looks Like slide, before Q&A. **Compare the results against Poll 1 out loud.** Saying the comparison in the room is what makes the audience feel the arc close, and it costs fifteen seconds.

**Why the options mirror.** Each Poll 2 option is the Poll 1 pain in its resolved state, in the same order. That does three things at once: it recaps the session without a recap slide, it lets someone who picked `03` at the start see exactly what changed for them, and it makes the two result sets directly comparable.

**Why it earns its slot.** It converts watching into a commitment, and the Poll 1 to Poll 2 delta tells you which section actually moved someone. That comparison is the most useful thing this session produces for Productside besides the registrations.

## Voice notes

Both polls follow the Copy Guidelines in the design system: second person, pain-led, conversational, no em dashes, no banned words.

**What they deliberately avoid:** repo, versioned, guardrails, evidence chain, and every other phrase that describes the mechanism instead of the result. The audience is product managers, not engineers. An option that names a thing you set up is an output. An option that names a thing that stops happening is an outcome, and outcomes are what Productside teaches.

**No option blames the team.** The pain is stated as a system failure, not as colleagues failing to comply.

**No option names a mechanism.** Repo, versioned, guardrails, evidence chain — all describe how it works rather than what it costs.

## For whoever loads these into the platform

- Two polls, one question each, five options each. Single choice, not multi-select — the whole point is forcing a priority.
- No "other" option and no free text. Five categories is the taxonomy the session teaches.
- Results need to be visible to the presenters in the moment, not just exported afterward.
- **Export both result sets after the session.** The comparison is the deliverable.
