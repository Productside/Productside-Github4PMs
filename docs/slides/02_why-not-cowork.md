&nbsp;

Cowork projects give you a folder, a history, and a way to share. The question is where it stops.

| | **Claude Cowork project** | **GitHub repo** |
|---|---|---|
| **File hierarchy** | Yes | Yes |
| **History** | Conversation history. You see what you asked and what Claude produced. | Commit history. Every change is named, dated, and attributed. |
| **Who changed what** | Unclear. Prompts and responses blur together. | Every commit names the author. Every line traces to a person and a moment. |
| **Experimentation** | Edit in place. If it fails, undo manually or lose the prior state. | Branch, try it, throw it away or merge it. Main never sees the experiment. |
| **Review gate** | None. Anyone with access can change any file. | Pull requests. Someone reviews before it reaches main. |
| **Tool portability** | Files live inside Claude's environment. | One clone, every tool. Claude Code, Cursor, VS Code, scripts, any AI assistant. |
| **Access control** | Share a link. Everyone gets the same access. | Granular. Read-only, write, admin. Teams, individuals, public, private. |
| **Vendor independence** | If you leave Claude, the project stays in Claude. | The repo is yours. Host it anywhere. No lock-in. |

&nbsp;

A Cowork project is a workspace. A repo is a **system of record**.

Start in Cowork. But when the work matters enough that you need attribution, review, and tool portability, that is when you move to a repo.

Kenny started exactly this way. He chose a GitHub repo because he wants commit history, branching, and the freedom to share it later on his terms.
